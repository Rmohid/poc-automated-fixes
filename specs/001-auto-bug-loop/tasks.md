## Phase 3: User Story 1 - Automatic Bug Detection and Issue Creation (Priority: P1) MVP

**Goal**: CI pipeline detects test/lint failures on push/PR and auto-creates a well-formatted GitHub Issue with failure details, labels, and Copilot Workspace call-to-action

**Independent Test**: Push a commit with a known test failure or lint error to a non-main branch and verify a GitHub Issue is created with `auto-fix` and `bug` labels, correct commit SHA, branch name, and truncated output

### Implementation for User Story 1

- [x] T007 [US1] Create the GitHub Actions workflow file with trigger config (`push` and `pull_request` on `branches-ignore: [main, master]`), Node.js 20 setup, and `npm ci` step in .github/workflows/auto-bug-detect.yml
- [x] T008 [US1] Add test execution step with `id: tests`, running `npm test 2>&1 | tee test-output.txt` with `continue-on-error: true` in .github/workflows/auto-bug-detect.yml
- [x] T009 [US1] Add lint execution step with `id: lint`, running `npm run lint 2>&1 | tee lint-output.txt` with `continue-on-error: true` in .github/workflows/auto-bug-detect.yml
- [x] T010 [US1] Add duplicate detection step using `actions/github-script@v7` that queries open issues with `auto-fix` label and checks if any issue body contains `context.ref` (branch name), outputting `duplicate_found` in .github/workflows/auto-bug-detect.yml
- [x] T011 [US1] Add issue creation step using `actions/github-script@v7` that reads `test-output.txt` and `lint-output.txt`, truncates each to 3,000 chars, and creates a GitHub Issue with title `[Auto] Build failure: {short-sha}`, labels `["auto-fix", "bug"]`, and structured body per issue-template contract in .github/workflows/auto-bug-detect.yml
- [x] T012 [US1] Add Copilot Workspace call-to-action text in the issue body footer: `*This issue was auto-generated by the CI pipeline. To propose a fix, open this issue in Copilot Workspace.*` in .github/workflows/auto-bug-detect.yml
- [x] T013 [US1] Add conditional logic: duplicate check runs only when `steps.tests.outcome == 'failure' || steps.lint.outcome == 'failure'`; issue creation runs only when failure detected AND `duplicate_found != 'true'` in .github/workflows/auto-bug-detect.yml

**Checkpoint**: At this point, pushing a failing commit to any non-main branch should auto-create a labeled GitHub Issue with failure details. Pushing a passing commit should create nothing. Consecutive pushes to the same broken branch should not duplicate issues.

## Dependencies & Execution Order

### Phase Dependencies

- **Setup (Phase 1)**: No dependencies - can start immediately
- **Foundational (Phase 2)**: N/A - no blocking prerequisites for this project
- **User Story 1 (Phase 3)**: Depends on Setup (Phase 1) completion
- **User Story 2 (Phase 4)**: Depends on User Story 1 (needs auto-created issues to exist)
- **User Story 3 (Phase 5)**: Depends on Setup (Phase 1) only - can run in parallel with US1
- **User Story 4 (Phase 6)**: Depends on User Story 1 (extends the workflow)
- **Polish (Phase 7)**: Depends on all user stories being complete

### User Story Dependencies

- **User Story 1 (P1)**: Can start after Setup - No dependencies on other stories
- **User Story 2 (P2)**: Depends on US1 (needs the workflow and auto-created issues)
- **User Story 3 (P3)**: Can start after Setup - Independent of US1 (sample app is separate from workflow)
- **User Story 4 (P4)**: Depends on US1 (extends the workflow with Jira step)

### Within Each User Story

- Workflow steps must be added in execution order (checkout → setup → install → test → lint → dedup → create → jira)
- Sample app modules can be created in parallel (different files)
- Documentation tasks can run in parallel with each other

### Parallel Opportunities

- T003, T004, T005 can run in parallel (different config files)
- T016, T017, T018, T019 can run in parallel (different source/test files)
- T024, T025 can run in parallel (different doc files)

## Implementation Strategy

### MVP First (User Story 1 Only)

1. Complete Phase 1: Setup (T001-T006)
2. Complete Phase 3: User Story 1 (T007-T013)
3. **STOP and VALIDATE**: Push a failing commit to verify issue creation
4. Deploy/demo if ready - the core loop is functional

### Incremental Delivery

1. Complete Setup → Foundation ready
2. Add User Story 1 (workflow) + User Story 3 (sample app) in parallel → Test loop end-to-end → MVP!
3. Add User Story 2 (Copilot Workspace template) → Verify workspace opens with context
4. Add User Story 4 (Jira sync) → Test with Jira credentials
5. Polish phase → Documentation and final validation

### Parallel Team Strategy

With multiple developers:

1. Team completes Setup together
2. Once Setup is done:
   - Developer A: User Story 1 (workflow) + User Story 2 (extends workflow)
   - Developer B: User Story 3 (sample app)
3. After US1 complete: Developer B picks up User Story 4 (Jira sync)
4. Both developers: Polish phase
